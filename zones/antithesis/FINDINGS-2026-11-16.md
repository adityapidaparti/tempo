# Tempo zones: findings

Code under test: `tempoxyz/tempo@8314f7ba` (quorum-handoff configuration). The product crates are
unmodified. The code involved in each finding is unchanged on `main` as of `1200580f`.

## Harness

**Topology** (`contrib/antithesis/zones/docker-compose.yaml`):

- `l1`: a single-node Tempo dev chain (`--dev.finality-depth 1`, 500 ms blocks). It is never faulted.
- `zone-0`, `zone-1`, `zone-2`: the sequencer quorum, threshold 2-of-3, with `zone-0` the initial
  leader. Each runs under a supervisor that can SIGKILL and restart it on request.
- `zone-rpc`: a non-quorum follower serving the user-facing RPC.
- `proxy-0`, `proxy-1`, `proxy-2`: per-sequencer TCP proxies on each node's L1 and P2P links, so one
  node's links can be held or released.
- `workload`: runs the test commands.

**Workload:**

- Tempo's drivers: deposits, transfers, withdrawals, fan-out, leader rotation through
  `setLeader`/`zone_setLeader`, and the handoff, outage and asymmetric-partition campaigns.
- One added driver, `lagging-backfill-crash`. Each episode:
  1. delays the leader's MDBX `msync`/`fsync` by 0–55 s, using a test-only `LD_PRELOAD` library that
     changes no data or ordering;
  2. makes one follower fall behind, by gating its P2P link, by restarting it, or by letting its 30 s
     inactivity probe fire;
  3. SIGKILLs the leader through the supervisor while the follower catches up;
  4. restarts the leader.

**Faults:** Antithesis `custom_faults` on `zone-0..2`: process kill, hang, CPU throttling, network
partitions and clogs, clock jitter, CPU modulation.

**Properties.** These are `always` assertions, evaluated by `anytime_consistency` while faults run:

| Property | Invariant |
|---|---|
| Zone nodes never hold different blocks at the same height | Every node that has height `h` has the same hash at `h` |
| Zone nodes agree with the block settled on L1 | Each node's block at the portal's `zoneHeight` equals the portal's `blockHash` |
| Finalized zone blocks never change | Once a node reports block `h` as `finalized` with hash `X`, it never later reports a different hash at `h` |
| Settled workload transactions stay final | A transaction whose receipt is in a block at or below L1's settled height keeps that receipt and block |
| Value is conserved between L1 escrow and the zone | Portal escrow equals zone supply plus pending deposits and withdrawals, at the settled height |

**Runs:**

| Run | Configuration | Result |
|---|---|---|
| `cd7fa72efe3499090edec427b85f97da-67-0` | All drivers, including `lagging-backfill-crash` | Findings 1 and 2 |
| `d5283b027a31fb07e072a67357671b64-67-0` | As above, plus the finality and conservation properties | Findings 1 and 2 |
| `c478afec…`, `0fb2b91a…` (3 nodes); `fe2df2c9…` (4 nodes); `f6a0a7b8…` (5 nodes) | No `lagging-backfill-crash`, no `LD_PRELOAD` library | All five properties held |
| `65999d8f…` (3 nodes), `d4aaa43e…` (4 nodes), 12 h each | As above | In progress; no safety-property failures so far |

## Finding 1: the leader serves blocks to followers before they are durable

**Invariant.** Every node that has height `h` has the same block at `h`, and each node's block at L1's
settled height is the block L1 settled.

**Failed properties:**

| Run | Property | Failures | Counterexample |
|---|---|---|---|
| `cd7fa72e` | Zone nodes never hold different blocks at the same height | 4,001 | `5941134734744779118` @ 102.25 |
| `cd7fa72e` | Zone nodes agree with the block settled on L1 | 24 | `8452130513324651711` @ 133.18 |
| `d5283b02` | Zone nodes never hold different blocks at the same height | 5,603 | `4288723881960817476` @ 101.76 |
| `d5283b02` | Zone nodes agree with the block settled on L1 | 42 | `-7350374959785930380` @ 144.36 |

**Counterexample `cd7fa72e` @ 102.25:**

- From 94.6, episode 0 delays leader zone-0's commits by 43–47 s while follower zone-1 catches up.
- At 99.78, zone-0 restarts with `healing via changesets checkpoint=143 sf_tip=144` and
  `Leader generation started epoch=1`.
- At 102.25, block 144 is `0xf630…` on zone-0 and `0x7d2f…` on zone-1, zone-2 and zone-rpc.

**Counterexample `d5283b02` @ 144.36:**

| vtime | Event |
|---|---|
| 133.7–137.2 | Leader zone-0 builds blocks 218–227 (221 = `0xa7cb…`); its MDBX checkpoint stays at 217 |
| 134.2 | zone-2 restarts |
| 139.3 | zone-2 backfills 218–227 from zone-0 |
| 139.7 | zone-0 proposes settlement of block 220, which is uncommitted on zone-0; zone-2 signs |
| 140.3 | zone-0 restarts: `checkpoint=217 sf_tip=227`; it rebuilds 218–227 (221 = `0xdfea…`) |
| 141.3–142.2 | zone-1 signs; L1 settles through 221 = `0xdfea…` |
| 144.36 | zone-2 holds 221 = `0xa7cb…` and rejects every new block |

**How to trace a counterexample:**

```sh
snouty runs properties cd7fa72efe3499090edec427b85f97da-67-0 --failing --json   # moments: input_hash, vtime
snouty runs logs cd7fa72efe3499090edec427b85f97da-67-0 --json -- 5941134734744779118 102.25 > ce.ndjson
jq -c 'select(.antithesis_assert.condition == false) | .antithesis_assert.details' ce.ndjson
jq -r 'select(.output_text // "" | test("healing via changesets checkpoint|Leader generation started|Imported canonical peer block|conflicts with canonical|parent mismatch")) | "\(.moment.vtime) \(.source.container) \(.output_text)"' ce.ndjson
```

In the output, look for:

- the leader logging `healing via changesets checkpoint=X sf_tip=Y`, with `Y > X`, at restart, followed by
  `Leader generation started`;
- before that restart, a follower logging `Imported canonical peer block block_number=…` for a height in
  `(X, Y]`;
- after it, the follower logging `peer block conflicts with canonical block` and
  `peer block parent mismatch`;
- the assertion details giving each node's hash at the divergent height.

Any reported moment can be replayed in an Antithesis debugging session at that `input_hash` and
`vtime`.

**Attempted root-cause analysis.**

reth's `DatabaseProvider::commit` (`storage/provider/src/providers/database/provider.rs:4083-4108`,
reth `31d05e14`) runs `static_file_provider.finalize()`, then the RocksDB batches, then the MDBX
commit. `last_block_number()` returns the static-file tip, so it includes block `H` before `H` is
durable. A crash between the steps leaves static files ahead of the MDBX checkpoint, and
`check_consistency` prunes them on restart, which is the `healing via changesets` line above.

The zone takes its chain tip from `last_block_number()` in the paths that send blocks to other nodes:

- backfill serving (`crates/zones/node/src/replication.rs:399`);
- drain at demotion (`:255`);
- broadcaster start and stop (`:122`, `:130`, `:176`);
- settlement batch preparation (`crates/zones/sequencer/src/monitor.rs:424`);
- the follower's signing gate (`crates/zones/node/src/follower.rs:420-427`).

The steady-state broadcast follows the persisted-block stream (`replication.rs:203`) and is not
affected. After the restart, the leader is still scheduled for the next anchor. It rebuilds height `H`
with a new hash, because the timestamp is `max(l1, wall, parent)` (`crates/zones/node/src/engine.rs:673`).
Followers holding the original reject it and every descendant (`follower.rs:~592`, `~610`), and nothing
reconciles them.

The same outcome occurs without the `LD_PRELOAD` library. Holding the leader's `mdbx_txn_commit_ex`
with gdb, letting the followers' inactivity probe backfill the held block, then SIGKILLing the leader
(`repro-2026-11-13-leader-fork/n2-gdb-hold.sh`) leaves the leader on `0xa9ae…` at 39. The other three
nodes stay on `0xc16d…` and stop advancing.

When L1 has already settled the lost block, the leader can no longer start:
`resolve_portal_zone_anchor` (`crates/zones/sequencer/src/settlement.rs:186`) cannot find the portal's
`blockHash`, and the role controller retries indefinitely (`failed to resolve portal-confirmed Zone
height for leader recovery`). This was reproduced once with gdb
(`repro-2026-11-13-leader-fork/n2b-settlement.sh`). The 139.7 step above is one step short of it.

**Impact:**

- A permanent fork between the leader and the quorum.
- Settlement stops.
- L1 can settle one chain while other nodes, including the user-facing RPC node, hold another.
- A permanent halt when the settled block is the lost one.

## Finding 2: the leader reports blocks as finalized before they are durable

**Invariant.** A block a node reports as `finalized` never changes, and a transaction with a receipt in
a settled block stays there.

**Failed properties:**

| Run | Property | Failures | Counterexample |
|---|---|---|---|
| `d5283b02` | Finalized zone blocks never change | 2,161 | `-5683151602728837615` @ 108.33 |
| `d5283b02` | Settled workload transactions stay final | 246 | `-8251040207591746424` @ 138.90 |
| `cd7fa72e` | Settled workload transactions stay final | 658 | `6392963380252419349` @ 138.82 |

**Counterexample `d5283b02` @ 108.33:**

- zone-0 reported block 145 as `finalized` with hash `0xeb5f…`.
- At 102.96 it restarted (`checkpoint=144 sf_tip=145`).
- At 108.33 it reports block 145 as `finalized` with hash `0x226c…`.

**Counterexample `cd7fa72e` @ 138.82:**

- Transaction `0x69b24474…` had a success receipt in block 151 from leader zone-0.
- zone-0 restarted (`checkpoint=147 sf_tip=148`) and rebuilt the following heights.
- The transaction is now in block 153.

**How to trace a counterexample:**

```sh
snouty runs logs d5283b027a31fb07e072a67357671b64-67-0 --json -- -5683151602728837615 108.34 > ce.ndjson
jq -c 'select(.antithesis_assert.condition == false) | .antithesis_assert.details' ce.ndjson
jq -r 'select(.output_text // "" | test("healing via changesets checkpoint|Leader generation started|Starting Tempo Zone")) | "\(.moment.vtime) \(.source.container) \(.output_text)"' ce.ndjson
```

In the output, look for:

- *Finalized zone blocks never change*: details `{node, height, old_hash, new_hash}`, with a
  `healing via changesets checkpoint=X sf_tip=Y` line on that node between the two observations,
  where `X < height <= Y`.
- *Settled workload transactions stay final*: details `{tx, recorded_block, receipt_block}`, with
  `receipt_block` different from `recorded_block` or the receipt `null`, and the same heal line on
  the leader that issued the original receipt.

**Attempted root-cause analysis.**

The leader sets head, safe and finalized to each new block as soon as it is built
(`crates/zones/node/src/engine.rs`, `forkchoice_state`: "The zone has instant finality so head = safe =
finalized"). reth serves the block's receipts and the `finalized` tag from `CanonicalInMemoryState`
immediately; persistence runs later on the persistence thread. A crash before the commit discards the
block. The leader then builds that height again, and the result depends on where the transaction was
in the pool:

- **Sent directly to the leader:** the transaction was only in the leader's in-memory pool, so it is
  gone.
- **Forwarded by a follower:** it is re-included later, under a newer timestamp and L1 state.

Measured on a local stack (`repro-2026-11-15-window/`), a block stays uncommitted for about
110–180 ms after its receipt is returned, out of a 500 ms block time, at loads up to about 355 tx/s. A
SIGKILL about 10 ms after a receipt lost the transaction in 30 of 30 trials at about 350 tx/s and 10 of
10 at idle. A graceful SIGTERM flushes all in-memory blocks in about 0.33 s and lost nothing in 24
trials.

Consequences reproduced on a local stack:

- **Double spend** (`repro-2026-11-13-leader-fork/n4-double-spend.sh`): a 900 pathUSD payment reported
  `finalized` disappeared after a leader crash. The same funds were then paid to another account and
  settled on L1.
- **Revoked key re-activated** (`repro-2026-11-13-leader-fork/keys/testA.sh`): a `revokeKey` reported
  `finalized` was gone after a leader crash. The revoked key then signed a successful transfer and
  authenticated to the private RPC.

**Impact.** An ungraceful leader exit (an OOM kill, a host failure or a power loss) loses its latest
finalized block with high probability. Acknowledged transactions disappear or change outcome, and the
chain afterwards gives no sign that history changed.
