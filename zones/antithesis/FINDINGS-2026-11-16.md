## 1. A sequencer restored from backup rewrites history it already published

**Severity: critical in the scenario below; the outcome depends on which nodes are running.**
Reproduced on unmodified `tempoxyz/tempo@8314f7ba` (Alexey's quorum-handoff configuration) on a local
stack. Scripts and logs: [repro-2026-11-14-restore/](repro-2026-11-14-restore/).

### Summary

When a sequencer starts, it works out its role only from its own local chain. If an operator
restores it from a backup (a routine disaster-recovery step) and the schedule still names it as
leader, it starts leading from the backup height and builds again every height after it. Those heights
were already produced, broadcast and acknowledged to users. The new blocks have different hashes.
Nothing compares the restored node's tip with what its peers hold before it takes leadership.

- Nodes that still hold the original blocks reject the rewritten ones, and the zone splits permanently.
- Nodes that were behind the backup height accept the rewritten blocks and sign settlements for them.
  If they make up the threshold, **L1 settles the rewritten history**, and transactions users were told
  had succeeded are erased from the settled chain.
- If L1 has already settled past the backup height, the restored leader cannot start at all, and the
  zone halts permanently.

### Why the checks don't catch it

- The role comes from the local checkpoint: `next_anchor = local tempo checkpoint + 1`, then
  `leader_for(next_anchor)` (`crates/zones/node/src/role.rs`).
- The promotion barrier is empty for ordinary transitions; only forced recovery has one
  (`role.rs`, `promotion_readiness`).
- Before leading, the node checks only that L1's last settled block exists locally
  (`crates/zones/sequencer/src/settlement.rs`, `resolve_portal_zone_anchor`). It never checks that its
  head is at least as high as what it, or its peers, have already published. The followers' reported
  tips (`PeerTipRegistry`) are never consulted for promotion.
- Followers keep no record of what they have signed, so a follower that is behind signs the
  rewritten blocks without conflict.

### Reproduction

**L1 settles the rewritten history** (`t1.sh`):

1. Both followers are down (stopped cleanly at height 183), so settlement stalls at 180. The leader
   keeps producing alone up to 223, and the user-facing RPC node follows it.
2. Three transfers are sent and receipted with `status 1` in blocks 189, 196 and 203.
3. The leader is stopped and restored from a backup taken at height 183. On start it logs
   `Promotion barrier satisfied … next_anchor=203` and `Leader generation started`, and rebuilds from
   184.

| Height | Original (RPC node) | Rewritten (restored leader) |
|---|---|---|
| 184 | `0xee7e18c0…` | `0x50133e3b…` |
| 193 | `0x2b210390…` | `0xdf3dd3a1…` |
| 203 | `0x1aa28092…` | `0x58e3b93d…` |

4. The followers come back. Both adopt the rewritten chain and sign. The first batch L1 accepts ends
   at the rewritten block 194 (`0x9ba3f122…`; the RPC node's 194 is `0x4dd46b3d…`), and L1 later
   settles through block 360 on the rewritten chain.
5. The three receipted transfers return `null` on all three sequencers but still show `status 1` on
   the RPC node. The RPC node rejects the rewritten blocks (`peer block conflicts with canonical block`,
   then `parent mismatch`) and stays at 227 permanently.

**Restore from a backup older than L1's settled height** (`t1a`): with a backup at 348 and L1 settled at
420, the restored leader logs `Promotion barrier satisfied` and then retries every 0.5 s with
`Role generation failed to start … failed to resolve portal-confirmed Zone height for leader recovery`.
It never catches up from its peers, and the zone produces no blocks.

**Not reproduced: up-to-date followers running** (`t2b.sh`). We restored the leader and one follower
while the other follower and the RPC node were current. The restored follower fetched the original
blocks from a current peer before the leader's rewrite reached it, so the rewrite never got a second
signature. The leader split off on its own and the zone halted, but L1 settled nothing wrong. This
happened in 2 of 2 attempts. Which chain a restored follower adopts depends on which peer answers its
catch-up request first.

### Preconditions, stated plainly

- A sequencer's data directory is restored from a backup while the schedule still names it as leader.
  There is no forced-recovery directive.
- For L1 to settle the rewritten history, the followers must be at or behind the backup height. In our
  run they were down during the leader's solo period; it could also be a follower outage followed by
  the leader's disk failing.
- With current followers running, the outcome is a permanent split and halt rather than a bad
  settlement.

### Impact

- **Erased acknowledged transactions on the L1-settled chain** in the scenario above, with users still
  seeing success on the RPC node that kept the original chain.
- **A permanent split or a permanent halt** in every other case we tried. None recovered without
  manual repair.

### Relation to the 2026-11-13 findings

- **It is not a durability race.** The original blocks were fully saved on every node before the
  restore, so fixing 2026-11-13 findings 1 and 2 does not fix this. The gap is that a node never checks
  its own published history, or its peers' tips, before leading.
- **L1 never settles both versions.** The portal requires each batch to extend the last settled hash,
  so it settles the rewritten chain *instead of* the original, which had not been settled yet.

### Suggested fix

- Before taking leadership, compare the local head with the tips peers report, and with the node's
  own published high-water mark kept outside the restorable datadir. Refuse to lead, and catch up
  instead, if the node is behind.
- Let a node that cannot resolve the portal's settled block catch up from peers instead of retrying
  leadership forever.
- Followers could keep a durable record of what they have signed and refuse to sign a different block
  at the same height.

## 2. Update to 2026-11-13 finding 2: how often "finalized" blocks are lost

The 2026-11-13 report said finding 2 needs a crash while saving lags behind, and that 30 plain kills
lost nothing. That kill path was slower than the window. Measured directly:

- **Any ungraceful leader crash is likely to hit it.** We measured the gap on unmodified code
  ([`repro-2026-11-15-window/`](repro-2026-11-15-window/)). After the leader returns a receipt and
  reports the block as `finalized`, that block stays unsaved for about **110–180 ms of every 500 ms
  block**, both idle and at full load (about 355 tx/s):

  | SIGKILL this long after the receipt | idle | ~350 tx/s |
  |---|---|---|
  | ~10 ms | 10/10 lost | 30/30 lost |
  | 50 ms | 5/5 lost | 5/5 lost |
  | 100 ms | 5/5 lost | 4/5 lost |
  | 175 ms | 5/5 kept | — |
  | 250 ms | 5/5 kept | 5/5 kept |

  Every loss was confirmed after catch-up on all four nodes: receipt `null`, sender nonce
  unchanged, and reth logging that the block was in static files but never committed. An
  out-of-memory kill, a host crash or a power loss of the leader therefore loses its most recent
  receipted, finalized block with high probability. (An earlier local test, where 30 kills lost
  nothing, used a kill path slower than this window.)
- **Routine deploys are safe.** A graceful SIGTERM flushes every in-memory block in about 0.33 s, so
  deploys with a 2 s, 10 s or 30 s grace period lost nothing across 24 runs.

Scripts and data: [repro-2026-11-15-window/](repro-2026-11-15-window/).

## 3. A request to move leadership back can be silently dropped

**Severity: medium.** This concerns admin leader selection and is non-deterministic: it depends on
whether the request lands inside L1's finality gap.

Leadership moves when the admin calls `setLeader` on L1, directly or through a sequencer's
`zone_setLeader` relay. The relay decides whether a change is needed by reading the portal's leader at
L1's **finalized** block (`crates/zones/node/src/rpc.rs`, `zone_setLeader`). If that leader already
equals the requested one, it replies `alreadyActive` and sends nothing.

Suppose the admin moves leadership from A to B, and the transaction is mined but not yet finalized.
Within that gap, a request to move leadership back to A reads the finalized leader (still A), gets
`alreadyActive`, and is dropped. Once B finalizes, B stays leader, although the most recent valid
request was for A. The usual reason to move leadership back quickly is that B is failing.

On unmodified code ([`repro-2026-11-15-relay/`](repro-2026-11-15-relay/)), with L1 finality lagging
about 4.5 s (`--dev.finality-depth 10`):

| Case | Result |
|---|---|
| `zone_setLeader(A)` sent within the gap after an admin A→B | **10/10 dropped**: reply `{"status":"alreadyActive",...}` within 70 ms, no transaction sent, B finalizes as leader |
| The same request after B has finalized (control) | 2/2 `submitted`; leadership moves back to A |
| The request relayed by a third node within the gap | 2/2 fail with a bare `-32603 … execution reverted` (`StaleLeadershipEpoch`), because the relay uses the finalized epoch while L1 checks against latest |

On the local L1 as shipped, finalized almost always equals latest (32,122 of 32,123 samples), so the
gap is effectively zero and the drop did not occur (0/10). How often this happens in production
depends on Tempo L1's finality lag.

A fix is to compare against the latest leader and epoch (or both), or to submit the transaction and
let the portal's epoch check decide, and to report a pending, unfinalized change instead of
`alreadyActive`.
