# Tempo zones: findings

Code tested: `tempoxyz/tempo@8314f7ba` (quorum-handoff configuration, three sequencers, 2-of-3
settlement threshold). Every finding reproduces on unmodified code. The code involved is unchanged
on `main` as of `1200580f`.

Reproduction scripts and logs are in the `repro-*` directories next to this file. They drive the
zones Docker harness in `contrib/antithesis/zones`.

| # | Finding | Severity |
|---|---|---|
| 1 | The leader serves blocks to followers before they are durable; a leader crash forks it from the quorum, and can halt the zone permanently | Critical |
| 2 | The leader reports blocks as finalized before they are durable; a leader crash undoes finalized transactions | Critical |
| 3 | A sequencer restored from a backup re-authors heights it already published | Critical |
| 4 | Bounce-back refunds credited to a virtual address can never be claimed | High |
| 5 | A graceful restart discards the node's pending local transactions | Medium |
| 6 | `zone_setLeader` drops a request whose target is the finalized leader while a different leader is pending | Medium |
| 7 | An HTTP JSON-RPC batch runs every call under the identity authenticated at its start | Medium-low |

## 1. The leader serves blocks to followers before they are durable

### Mechanism

reth persists a block in two steps inside `DatabaseProvider::commit`
(`storage/provider/src/providers/database/provider.rs:4083-4108` at reth `31d05e14`):

1. `static_file_provider.finalize()` writes the block to the static files and advances the
   static-file index;
2. the RocksDB batches and the MDBX transaction commit.

`BlockchainProvider::last_block_number()` returns the static-file tip, so it reports block `H` after
step 1. If the process dies between the two steps, `check_consistency` on the next start finds the
static files ahead of the MDBX checkpoint and prunes them back (`healing via changesets
checkpoint=H-1 sf_tip=H`).

The zone uses `last_block_number()` as its chain tip wherever it publishes blocks to other nodes:

| Path | Location |
|---|---|
| Backfill pages served to followers | `crates/zones/node/src/replication.rs:399` (`serve_backfill_page`) |
| Drain at demotion | `replication.rs:255` |
| Broadcaster start and stop | `replication.rs:122`, `:130`, `:176` |
| Settlement batch preparation | `crates/zones/sequencer/src/monitor.rs:424` |
| Follower signing gate (`height <= last_block_number`) | `crates/zones/node/src/follower.rs:420-427` |

The steady-state broadcast is safe because it follows the persisted-block stream (`replication.rs:203`).
The paths above are not.

If the leader serves `H` inside that window and then crashes, it restarts at `H-1`. It is still the
scheduled leader, so it builds a new block at height `H`. That block has a different hash, because the
timestamp is `max(l1, wall clock, parent)` (`crates/zones/node/src/engine.rs:673`). Followers holding
the original `H` reject it (`peer block conflicts with canonical block`, `follower.rs:~592`) and every
block after it (`peer block parent mismatch`, `follower.rs:~610`). Nothing repairs this:

- followers never unwind;
- the leader ignores incoming blocks (`replication.rs:527-532`);
- promotion does not consult peer tips (`crates/zones/node/src/role.rs:582`).

### Reproduction

`repro-2026-11-13-leader-fork/n2-gdb-hold.sh` and `n2-impact.sh`, on a local stack:

1. Attach gdb to the leader in non-stop mode and break on `mdbx_txn_commit_ex`. Only the
   `mdbx-rs-txn-mgr` thread stops; the persistence thread is blocked in `DatabaseProvider::commit`
   after `finalize()`.
2. The followers' 30 s inactivity probe backfills the uncommitted block from the leader.
3. SIGKILL the leader and restart it.

Result (`n2-impact.sh`):

| Node | Hash at 156 | Tip after 10 min |
|---|---|---|
| zone-0 (leader) | `0xddab…` | 1198 |
| zone-1, zone-2, zone-rpc | `0x24f3…` | 156 |

The leader had logged `checkpoint=153 sf_tip=156` and rebuilt blocks 154–156. After the fork, the
leader submitted no settlement batches; zone-1 rejected 1,044 settlement proposals and 493 blocks. A
transfer sent to the leader after the fork has a success receipt on the leader and none on any other
node.

The same fork appears in Antithesis runs:

- `1b900239d3de50bcf4a2b9e2cbc8ed1a-67-0`: property *Zone nodes never hold different blocks at the
  same height*.
- `d5283b027a31fb07e072a67357671b64-67-0`: property *Zone nodes agree with the block settled on L1*.
  In counterexample `-7350374959785930380`:
  - leader zone-0 served blocks 218–227 to a restarting zone-2 while its saved head was 217;
  - zone-0 was killed and rebuilt 218–227;
  - zone-1 signed the rebuilt chain and L1 settled it through 221;
  - zone-2 kept the original chain and rejects every new block.
  
  In another counterexample (`-3576764051148361626`), zone-1 and zone-rpc are left on the abandoned
  chain.

These runs widen the window with an `LD_PRELOAD` library that delays `msync`/`fsync` on `mdbx.dat`. The
library changes no data or ordering; the gdb reproduction does not use it.

### When L1 has already settled the lost block

`BatchPreparer` and the follower signing gate also use `last_block_number()`, so a batch can be
proposed, signed and submitted for a block that exists only in the leader's static files. If L1
accepts it and the leader then loses the block, the portal's `blockHash` refers to a block the leader
does not have. Leader start-up requires that block (`resolve_portal_zone_anchor`,
`crates/zones/sequencer/src/settlement.rs:186`), so the node fails and retries every 0.5 s
indefinitely:

```
ERROR zone::role: Role generation failed to start; fencing before retry generation=849 role="leader"
      err=failed to resolve portal-confirmed Zone height for leader recovery
```

A fenced node runs no follower tasks (`role.rs:858`), so it never fetches the block from the followers
that hold it. The followers cannot lead, because the schedule still names this node. The zone produces
no blocks again until an operator intervenes.

This was reproduced once by holding the commit on a batch-boundary block
(`repro-2026-11-13-leader-fork/n2b-settlement.sh`):

| | Value |
|---|---|
| Portal | `zoneHeight 13920`, `blockHash 0x3315be20…` |
| Leader | tip 13919; block `0x3315…` not found |
| Followers | tip 13920; no new blocks |

The same sequence appears in Antithesis run `d5283b02`, cut short by the kill landing before
submission. There, the leader proposed settlement of its unsaved block 220 and zone-2 signed it.

### Impact

- **Permanent fork.** The quorum and the user RPC node reject every block the leader produces.
- **Settlement stops.** Withdrawals stop being finalized.
- **Receipts the leader issues after the fork** are for a chain that cannot settle.
- **Inconsistent recovery.** L1 can settle one chain while other nodes, including the RPC node users
  read from, hold another.
- **Permanent halt** when L1 has already settled the lost block.

## 2. The leader reports blocks as finalized before they are durable

### Mechanism

The leader sets head, safe and finalized to each new block as soon as it builds it
(`crates/zones/node/src/engine.rs`, `forkchoice_state`: "The zone has instant finality so head = safe =
finalized"). reth inserts the block into `CanonicalInMemoryState` and serves its receipts and the
`finalized` tag immediately. Persistence happens afterwards, on the persistence thread.

If the leader dies before that block is committed, reth discards it on restart, and the leader builds
that height again. Whether the rebuilt block contains the same transactions depends on the pool:

- **Sent directly to the leader:** the transaction was only in the leader's in-memory pool. It is gone.
- **Sent through a follower:** the follower forwards it again, so it is included later, in a different
  block, under a newer timestamp and L1 state. A transaction that had a `status 1` receipt can
  execute again with a different outcome.

Deposit credits and withdrawal requests in the lost block behave the same way.

### Size of the window

`repro-2026-11-15-window/` measures it directly. A block remains uncommitted for about 110–180 ms after
its receipt is returned, out of a 500 ms block time, independent of load up to about 355 tx/s.

| SIGKILL this long after the receipt | idle | ~350 tx/s |
|---|---|---|
| ~10 ms | 10/10 lost | 30/30 lost |
| 50 ms | 5/5 lost | 5/5 lost |
| 100 ms | 5/5 lost | 4/5 lost |
| 175 ms | 5/5 kept | — |
| 250 ms | 5/5 kept | 5/5 kept |

Each loss was checked on all four nodes after catch-up: the receipt is `null` and the sender's nonce is
unchanged. reth logged that the block was in the static files but never committed. A graceful SIGTERM
flushes every in-memory block in about 0.33 s, so deploys with a 2 s, 10 s or 30 s grace period lost
nothing in 24 runs. The trigger is an ungraceful exit: an OOM kill, a host failure or a power loss.

### Double spend (`repro-2026-11-13-leader-fork/n4-double-spend.sh`)

| Step | Result |
|---|---|
| Alice pays a merchant 900 pathUSD | `status 1` in block 164; the leader reports block 170 as `finalized`; the merchant's balance shows the payment |
| The leader crashes and restarts | The payment is gone from every node; Alice's balance is restored |
| Alice pays Bob the same 900 pathUSD | `status 1` in block 203; L1 settles through block 220 |
| End state on all four nodes | The merchant has nothing; Bob has the funds |

### Revoked key re-activated (`repro-2026-11-13-leader-fork/keys/testA.sh`)

| Step | Result |
|---|---|
| Account V revokes access key K | `status 1` in block 235; the leader reports block 241 as `finalized` |
| The leader crashes and restarts | `getKey` shows K active on every node; the revoke receipt is `null` |
| K is used | A K-signed transfer from V succeeds in block 252; a K-signed token gets HTTP 200 from the private RPC |

### Antithesis evidence

Property *Settled workload transactions stay final*:

- **Run `1b900239`:** 45 transactions had a receipt from a block that was later discarded, and 22 were
  never included again. Transaction `0xefde8a3c…` had a success receipt in block 470 and was absent from
  the chain L1 settled through 486.
- **Run `cd7fa72e`:** a receipted transaction moved from block 151 to block 153 after a leader kill.

### Impact

- Any ungraceful leader exit loses the latest finalized block with high probability.
- Payments and other acknowledged actions disappear or change outcome, which permits a double spend.
- A finalized key revocation can be undone.
- After the crash the chain is consistent and nothing reports that history changed.

## 3. A sequencer restored from a backup re-authors heights it already published

### Mechanism

At start-up a sequencer derives its role from its own chain:

- it takes `next_anchor = local checkpoint + 1` and becomes leader if `leader_for(next_anchor)` is
  itself (`role.rs:515-523`);
- the promotion barrier is empty for ordinary transitions (`role.rs:558-583`);
- the only pre-production check is that L1's last settled block exists locally
  (`resolve_portal_zone_anchor`).

Nothing compares the local tip with what the node, or its peers, already published.
`PeerTipRegistry` is not consulted for promotion. Followers keep no record of what they signed.

A leader restored from a backup taken at height `H_b` therefore produces new blocks from `H_b+1`, with
new hashes, even though it had already produced and broadcast those heights.

- Nodes holding the originals reject the new blocks.
- Nodes at or below `H_b` accept them and sign settlement for them.

This is separate from findings 1 and 2: the original blocks were fully committed on every node.

### Reproduction (`repro-2026-11-14-restore/t1.sh`)

1. Both followers stop cleanly at 183, so settlement stalls at 180. The leader keeps producing to
   223, and zone-rpc follows it.
2. Transfers are receipted with `status 1` in blocks 189, 196 and 203.
3. The leader is stopped and its datadir restored from a backup taken at 183. It logs
   `Promotion barrier satisfied … next_anchor=203` and `Leader generation started`, and produces from
   184:

   | Height | Original (zone-rpc) | Re-authored (leader) |
   |---|---|---|
   | 184 | `0xee7e18c0…` | `0x50133e3b…` |
   | 193 | `0x2b210390…` | `0xdf3dd3a1…` |
   | 203 | `0x1aa28092…` | `0x58e3b93d…` |

4. The followers start, adopt the re-authored chain and sign it. L1 settles a batch ending at the
   re-authored block 194 and later settles through block 360.
5. The three receipted transfers are `null` on all three sequencers, and still `status 1` on zone-rpc.
   zone-rpc rejects the re-authored blocks and stays at 227.

### Other cases

- **Backup older than L1's settled height** (`t1a`): the restored leader fails to start indefinitely
  with the same `failed to resolve portal-confirmed Zone height` error as in finding 1. It does not
  catch up from its peers, and the zone produces no blocks.
- **Up-to-date followers running** (`t2b.sh`): a follower restored at the same time fetched the
  original blocks from an up-to-date peer before the re-authored ones reached it. The re-authored chain
  never gained a second signature, so the restored leader split off alone and the zone halted.

### Impact

- With followers behind the backup height, L1 settles a re-authored history and erases receipted
  transactions.
- Otherwise, a permanent split or a permanent halt.

## 4. Bounce-back refunds credited to a virtual address can never be claimed

### Mechanism

When a bounce-back cannot be delivered, the refund is parked under the recipient address:

- **L1:** `refunds[token][recipient]`, claimed with `claimRefund`, which pays only `msg.sender`
  (`ZonePortal.sol:1241-1257`).
- **Zone:** `withdrawal_bounce_backs[token][recipient]`, claimed with `claim_refund(caller)`
  (`crates/zones/precompiles/src/inbox/mod.rs:310-321`, `:367`).

Both sides accept a TIP-1022 virtual address (`masterId ‖ 0xFD×10 ‖ userTag`) as the refund or
fallback recipient: the deposit's `tempoRefundRecipient` (`ZonePortal.sol:1014-1024`) and the
withdrawal's `zoneFallbackRecipient` (`outbox/mod.rs:159`). A virtual address cannot sign, so it can
never claim. The master cannot claim it either, because the entry is not keyed by the master. There is
no other path out of either map.

The zone has no address registry, so a TIP-20 mint to any virtual address fails there. Every zone-side
bounce-back to a virtual fallback recipient is therefore parked.

This violates `TEMPO-ZONE-BOUNCEBACK-FUNDS-PRESERVED` in `zones/invariants.md`.

### Reproduction (`repro-2026-11-13-leader-fork/refund/`)

| Case | Result | Stuck in escrow |
|---|---|---|
| A zone withdrawal with a virtual fallback recipient bounces on L1 (`zone-variant.sh`) | `refunds(pathUSD, V) = 1e8` in the inbox; `claim_refund` from the user reverts `NoRefund` | 1e8 |
| An undecryptable deposit with an unregistered virtual refund recipient (`l1-variant.sh`) | `refunds(pathUSD, V) = 5e7` on the portal; the depositor's `claimRefund` returns 0 | 5e7 |
| A virtual address of a registered master, with the master temporarily blocking inbound transfers (`l1-registered.sh`) | Refunds to the master itself are recovered once the block lifts; the refund parked under V is not | 3e7 |

In each case the user's balance falls by the amount and the portal keeps it.

### Impact

Permanent loss of user funds, with no operator path to recover them. Exchanges commonly give users
virtual deposit addresses.

## 5. A graceful restart discards the node's pending local transactions

### Mechanism

On a graceful shutdown, reth saves pending local transactions to `txpool-transactions-backup.rlp` and
reinserts them at start-up (reth `transaction-pool/src/maintain.rs:~766`). On a zone node that
reinsertion runs before the enabled-token registry is populated (`crates/zones/node/src/node.rs:274`;
discovery happens later, at `:644`). Zone validation requires a balance in an enabled token
(`node.rs:1956`), so every restored transaction is rejected. reth deletes the backup without checking
the insertion results.

### Reproduction (`repro-2026-11-13-leader-fork/txbackup/txbackup.sh`)

Follower zone-2 is cut off from its peers and holds a pending transfer.

| Time | Event |
|---|---|
| 11:35:01 | `Saving current local transactions … num_txs=1`; the file contains the raw transaction |
| 11:35:03.546 | `Successfully reinserted local transactions from file … num_txs=1` |
| 11:35:03.559 | `Discovered enabled tokens from L1` |
| 11:35:09 | The pool is empty and the backup file is deleted |
| next 60 s | The transaction never appears on any node |
| 11:36:14 | The identical raw transaction is resubmitted and mined in block 1128 |

A transaction the node had already forwarded to the leader survives. One it had not is lost.

## 6. `zone_setLeader` drops a request whose target is the finalized leader while a different leader is pending

### Mechanism

`zone_setLeader` reads `leader()` and `leaderEpoch()` at L1's finalized block and returns
`alreadyActive` without sending a transaction when the target equals that leader
(`crates/zones/node/src/rpc.rs:1778-1789`). If `setLeader(B)` has been mined but not finalized, a
request to make A leader again sees A as the finalized leader. It is answered `alreadyActive` and
dropped. B becomes leader when its transaction finalizes.

A third relay asked in the same window builds the transaction against the finalized epoch. L1 checks
the latest epoch, so the transaction fails gas estimation with `StaleLeadershipEpoch`, and the relay
returns a bare `-32603 … execution reverted` with no transaction hash.

### Reproduction (`repro-2026-11-15-relay/`, L1 with `--dev.finality-depth 10`)

| Case | Result |
|---|---|
| `zone_setLeader(A)` sent while `setLeader(B)` is mined but not finalized | 10/10 answered `{"status":"alreadyActive",…}`; no transaction; B leads |
| The same call after B is finalized | 2/2 `submitted`; A leads |
| The call sent to a third relay inside the window | 2/2 `-32603 … execution reverted` (`StaleLeadershipEpoch`) |

On the stock local L1, finalized equals latest almost always, so the window is effectively closed there.

## 7. An HTTP JSON-RPC batch runs every call under the identity authenticated at its start

### Mechanism

The private RPC authenticates once per HTTP request (`crates/zones/rpc/src/server.rs:268`) and runs
every call in a batch under that `AuthContext` (`server.rs:200-209`). It does not re-check revocation
or expiry between calls. `zone_getEncryptionKey` awaits L1 with no timeout (`node/src/rpc.rs:771`), so
a batch can run for as long as L1 is slow.

### Reproduction (`repro-2026-11-13-leader-fork/auth/claim2.sh`)

The test batch is `[zone_getEncryptionKey, eth_getLogs(new blocks, account V)]`, signed with V's access
key K. Only the RPC's L1 connection is delayed, by 4–6 s. While the batch waits, V revokes K and makes
10 transfers.

| Run | Revoke block | Separate request with the same token | Batch |
|---|---|---|---|
| 1 | 1890 | 403 `keychain key revoked` | 200, with 18 of V's logs from blocks 1891–1894 |
| 2 | 1925 | 403 | 200, 16 logs from 1926–1929 |
| 3 | 1949 | 403 | 200, 16 logs from 1950–1953 |

The data returned belongs to the account that had authorized K.
