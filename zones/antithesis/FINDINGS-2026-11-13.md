# Findings, 2026-11-13: what a single zone-leader crash can do

These are two new findings from the 2026-11-13 Antithesis work on the Tempo zone sequencer. They are
separate from the earlier [FINDINGS.md](FINDINGS.md) and do not repeat anything in it.

1. [A single leader crash can split a zone permanently](#finding-1-a-single-leader-crash-can-split-a-zone-permanently)
2. [Transactions confirmed as final can disappear after a leader crash, enabling a double spend and undoing key revocations](#finding-2-transactions-confirmed-as-final-can-disappear-after-a-leader-crash)

Both come from the same habit: the leader treats a block as settled before it has saved it.
Finding 1 is the leader giving that block to other nodes; finding 2 is the leader giving it to
users. They need separate fixes.

- **Code tested:** `tempoxyz/tempo@8314f7ba`, Alexey's quorum-handoff configuration
  (branch `test/zones-quorum-handoff-campaign`). The bug reproduces with the product code
  unmodified.
- **Antithesis runs:** `1b900239d3de50bcf4a2b9e2cbc8ed1a-67-0` and `cd7fa72efe3499090edec427b85f97da-67-0`
  (unmodified product code), on the Tempo tenant.
- **Failing properties:** *Zone nodes never hold different blocks at the same height* (finding 1);
  *Settled workload transactions stay final* (finding 2).

## Finding 1: a single leader crash can split a zone permanently

### Summary

The zone leader sometimes sends followers a block before it has finished saving that block to
its own database. If the leader crashes at that moment, it restarts without the block and builds
a different one at the same height. The followers still hold the original, so from then on they
reject everything the leader produces.

The leader carries on alone. Its RPC looks healthy and it keeps returning receipts, but
those receipts are for a chain nobody else will accept. Every other node, including the RPC node
users read from, stays at the last shared block, and L1 settlement stops because the followers
will not sign the leader's batches. Nothing in the system detects or repairs the split. The usual
remedy, handing leadership to a follower on L1 with `setLeader`, cannot work here, so an operator
has to repair the nodes by hand.

It takes one crash at the wrong moment. There is no partition and no misbehaving node.

### Background: how a zone stays in sync

A zone runs three sequencer nodes. One is the leader and produces every block; the other two are
followers. Followers receive blocks in two ways:

1. **Live broadcast.** After the leader saves a block, it pushes the block to the followers.
2. **Catch-up (backfill).** A follower that has fallen behind asks the leader for the blocks it is
   missing, in pages. A follower falls behind when it has just restarted, when a network partition
   has just healed, or when it has heard nothing for 30 seconds, in which case it probes the
   leader.

Followers never rewrite history. If a block arrives that conflicts with one they already hold,
they reject it.

### What goes wrong

Each zone node is built on reth. reth saves each block in two steps:

1. It writes the block to its *static files* and marks them complete (`finalize`).
2. It commits the database transaction (MDBX) that records the block as saved.

The block is safe only after step 2. If the process dies between the two steps, reth notices on
the next start that the static files are ahead of the database, deletes the extra block and
carries on from the last committed one. Inside reth that is correct, because no part of reth has
told anyone else about the block yet.

The zone code does tell others. To decide how far its chain goes, it asks reth for
`last_block_number()`, and that number moves forward at step 1, not step 2. So for a moment the
leader believes block H is part of its chain when H is not yet saved, and it hands H out.

The live-broadcast path does not have this problem, because it waits for reth's "block saved"
notification. Other paths ask `last_block_number()` directly. All of them are in
`crates/zones/node/src/replication.rs`, apart from settlement preparation, which is in
`crates/zones/sequencer/src/monitor.rs`:

| Where the leader publishes | What it uses the number for |
|---|---|
| Catch-up pages for followers (`serve_backfill_page`) | How far each page goes |
| The final flush when a leader hands over (`Drain`) | Which blocks to push before stepping down |
| Broadcaster start and stop | Which blocks to push |
| Settlement preparation | How far the next L1 batch may reach |

#### The sequence

1. The leader produces block H. reth finishes step 1, so `last_block_number()` returns H.
2. A follower that is catching up asks for blocks. The leader serves H from memory, and the
   follower imports it and saves it to its own disk.
3. The leader crashes before step 2.
4. On restart reth deletes H. Its log shows
   `healing via changesets checkpoint=H-1 sf_tip=H`.
5. The leader is still the scheduled leader, so it builds a new block at height H. The new block
   H′ has a different hash: its timestamp comes from the wall clock, and its transactions and L1
   inputs can differ too.
6. The leader broadcasts H′. A follower holding H rejects it with *peer block conflicts with
   canonical block at height H*. It then rejects every block on top of H′ with *peer block parent
   mismatch at height H+1*, and keeps doing so.

#### Why it never heals

- Followers have no way to undo a block. When a block is rejected, a follower asks the leader for
  more blocks, gets the same conflicting ones back, and rejects them again.
- The leader ignores blocks from followers and never checks that its chain matches theirs, so it
  never notices the split.
- Handing leadership to a follower with `setLeader` does not help. A follower may take over only
  from a block that already includes the handover, and the blocks leading up to it exist only on
  the old leader's chain. No node produces, so the zone stops completely.
- Repair needs an operator. Either use the manifest forced-recovery procedure to name a follower
  and the hash of H, or rebuild every node from one surviving copy. In both cases the other side's
  data has to be wiped.

### How we found it

#### Where to look

We read the replication and persistence code looking for any moment when the leader could show
followers something it could still lose in a crash. The `last_block_number()` calls stood out:
reth advances that number at step 1 rather than step 2. We then confirmed in reth's source and
on running nodes that the gap is real.

#### Making the window big enough to hit

Normally the gap between step 1 and step 2 is a few milliseconds per block. That is open on every
block, but random crashes rarely land in it, so we gave Antithesis two test-only tools:

- **A slow-disk fault.** A small library is loaded into each zone node. When the test switches it
  on, it delays the database's `msync`/`fsync` on `mdbx.dat` by a set number of milliseconds, up to
  45 seconds. It changes no data and no ordering; it simulates a disk that has stalled.
- **A crash driver.** Antithesis runs it alongside the normal workload. In each episode it:
  1. switches the slow-disk fault on for the leader;
  2. makes a follower fall behind, by cutting its P2P link or restarting it;
  3. lets the follower catch up;
  4. kills the leader;
  5. checks that every node agrees on every block.

The fork check is a separate always-property. It compares block hashes across all four zone
nodes at every height they have in common and fails on any difference.

#### What Antithesis found

Antithesis found the split 13 minutes into the run. It ran with every fault type on the zone
nodes: crashes, pauses, CPU slowdown, network faults and clock jitter.

| Time (s) | What happened |
|---|---|
| 105.6 | Leader zone-1 starts saving block 166 on a stalled disk. Follower zone-2's P2P link is cut. |
| 107.7 | The RPC node catches up and receives block 166 (`0x7383…`) from the leader. |
| 141.3 | The link heals. zone-0 and zone-2 catch up and receive the same block 166 (`0x7383…`). |
| ~141.9 | The leader, zone-1, is killed. |
| 187.4 | zone-1 restarts, deletes block 166 (`checkpoint=165 sf_tip=166`) and resumes as leader. It builds a new block 166 (`0x3bde…`). |
| 189.85 | The fork check fails. The leader holds `0x3bde…`; the other three nodes hold `0x7383…`. |

#### Antithesis also finds L1 settling one chain while users read another

A second run on unmodified product code (`d5283b027a31fb07e072a67357671b64-67-0`) adds a check that
every node's block at L1's settled height matches the hash L1 recorded. That check failed 16 times.
In the first counterexample (input hash `-7350374959785930380`, vtime 144.36):

| Time (s) | What happened |
|---|---|
| 133.7–137.2 | Leader zone-0 builds blocks 218–227 (block 221 = `0xa7cb…`) while its database commit is slow; its saved head stays at 217 |
| 134.2 | Follower zone-2 restarts |
| 139.3 | zone-2 catches up from the leader and receives the unsaved blocks 218–227 |
| 139.7 | The leader proposes settlement of its unsaved block 220 and zone-2 signs it, but the leader is killed before submitting |
| 140.3 | zone-0 restarts, discards 218–227 (`checkpoint=217 sf_tip=227`) and rebuilds them: block 221 = `0xdfea…` |
| 141.3–142.2 | zone-1 signs, and L1 settles the rebuilt chain through block 221 |
| 144.4 | zone-2 still holds `0xa7cb…` at 221 and rejects every new block |

In another counterexample (input hash `-3576764051148361626`), the stranded nodes were zone-1 and the
user-facing RPC node, two of the four nodes, while L1 settled the chain held by the other two.

The 139.7 step is one step short of the worst case described below. The leader proposed a settlement
for a block it had not saved, and a follower signed it. Only the timing of the kill kept L1 from
settling it.

#### Reproducing it without Antithesis's help

To show the bug is in the product, not in our test tools, we reproduced it locally on a zone stack
built from unmodified `8314f7ba`. The slow-disk library is present in that image but set to 0 ms,
which passes every call straight through; gdb provides the delay instead:

1. Attach gdb to the leader. Pause only the thread that performs the database commit, at the start
   of the commit. Everything else keeps running.
2. The leader stops broadcasting, because no block is ever marked saved. After 30 seconds the
   followers probe for missing blocks, and the leader serves them the unsaved one.
3. Kill the leader and start it again.

The leader lost blocks 154–156 and rebuilt all three with different hashes. We then sent a pathUSD
transfer to the leader and watched the zone for ten minutes.

| Node | Chain height | Receipt for the transfer |
|---|---|---|
| zone-0 (leader) | 1198 and rising | success, block 187 |
| zone-1 | 156, stuck | none |
| zone-2 | 156, stuck | none |
| zone-rpc (users) | 156, stuck | none |

The leader had submitted 15 settlement batches to L1 before the split and none after. Over those
ten minutes zone-1 rejected the leader's settlement proposals 1,044 times and its blocks 493
times.

The scripts are in [repro-2026-11-13-leader-fork/](repro-2026-11-13-leader-fork/), with the logs
of each run.

### Impact

- **The zone stops for everyone but the leader.** The followers and the user-facing RPC node freeze
  at the last shared block. Deposits, transfers and new withdrawals stop. Withdrawals already settled on
  L1 can still be paid.
- **Settlement stops.** A batch needs two of the three sequencers to sign, and followers sign only
  batches that match their own chain. The leader keeps proposing and never collects a second
  signature.
- **Users get receipts for transactions that will not survive.** Anything sent to the leader after
  the split gets a success receipt for a block no other node accepts. When an operator repairs the
  zone onto the followers' chain, those blocks are discarded. Transactions that came in through a
  follower may be replayed on the surviving chain, possibly with different results.
- **The outage is hard to see.** The leader's RPC keeps reporting a growing chain and successful
  transactions.
- **Recovery is manual.** `setLeader` cannot fix it, as described above.

#### The worst case: L1 settles a block the leader then loses, and the zone is dead

The same gap reaches settlement. The leader decides how far a settlement batch may go from
`last_block_number()` (`crates/zones/sequencer/src/monitor.rs`). Followers sign a batch only if they
hold its last block (`crates/zones/node/src/follower.rs`), which they can do because they got that
block from the leader inside the gap. So the whole settlement round can complete on a block the
leader has not saved:

1. The leader produces block 13920, the last block of a settlement batch (batches close every 20
   blocks). Its save of 13920 is stuck between step 1 and step 2.
2. The followers have heard nothing for 30 seconds, probe the leader, and receive 13920.
3. The leader proposes the batch ending at 13920. Both followers sign it, and the leader submits it.
   L1 accepts it: the zone portal now records `zoneHeight = 13920`,
   `blockHash = 0x3315be20…428f2d`.
4. The leader crashes. On restart it discards 13920 (`checkpoint=13919 sf_tip=13920`).

Now L1 says the zone is settled through a block the leader no longer has. Before it can lead, the
leader must find the portal's settled block in its own chain
(`crates/zones/sequencer/src/settlement.rs`, `resolve_portal_zone_anchor`). It cannot, so leader
start-up fails, and it retries every half second forever:

```
ERROR zone::role: Role generation failed to start; fencing before retry generation=849 role="leader"
      err=failed to resolve portal-confirmed Zone height for leader recovery
```

The followers and the RPC node hold block 13920 but cannot produce, because the L1 schedule still
names the old leader. A node stuck in this state starts no catch-up, so the leader never fetches
13920 back from the followers that have an identical copy. Nothing produces blocks again until an
operator steps in.

We reproduced this once on unmodified `8314f7ba`, by timing the gdb hold so that it landed on a
batch-boundary block. An independent rerun of the script did not land the hold on a boundary
block in 30 attempts, so treat this run as a single observation.

Script: [`n2b-settlement.sh`](repro-2026-11-13-leader-fork/n2b-settlement.sh). gdb held the leader's
commit on a batch-boundary block, and then we killed the leader once L1 had accepted the batch.

| After the crash | Value |
|---|---|
| L1 portal | `zoneHeight 13920`, `blockHash 0x3315be20…428f2d` |
| Leader (zone-0) | tip 13919; block `0x3315…` not found; 849 failed leader start-ups in ~7 minutes |
| zone-1, zone-2, zone-rpc | tip 13920, no new blocks |

One crash at the wrong moment, with no operator mistake, leaves the zone permanently stopped.

### How likely it is in production

- **Every block passes through the gap.** The zone saves each block as soon as it is produced.
- **A follower is often catching up.** That happens after any restart, after any partition heals,
  and after 30 seconds without blocks.
- **The gap is short on a healthy disk** (milliseconds), but it grows with any disk stall: busy
  cloud volumes, noisy neighbours, slow `fsync`.
- **The crash can be anything:** an out-of-memory kill, a deploy, a node failure.

### Suggested fix (finding 1)

- Only send what is saved. Wherever the leader publishes blocks (catch-up pages, the
  handover flush, broadcaster start and stop, settlement preparation, and the followers'
  signing check), use the last block reth has reported as saved, not `last_block_number()`.
- Defence in depth: a leader that restarts behind its followers should catch up from them before
  producing again, rather than rebuilding heights it has already given out.

## Finding 2: transactions confirmed as final can disappear after a leader crash

### Summary

The zone leader tells users a transaction is done before it has saved the block that contains it.
It returns a success receipt, and it reports the block as `finalized`: the zone has "instant
finality", so the leader marks every new block head, safe and finalized at once
(`crates/zones/node/src/engine.rs`, `forkchoice_state`). Saving happens afterwards, in the
background.

If the leader crashes in between, reth discards the unsaved blocks on restart and the leader builds
those heights again. The rebuilt blocks need not contain the same transactions. The transaction the
user was told succeeded, in a block reported as final, either moves to a later block or vanishes:
no node has it, the sender's balance is untouched, and the chain carries on as if it never
happened.

Unlike finding 1, nothing looks wrong afterwards. All nodes agree, the zone keeps producing, and
L1 settlement continues. The only trace is a receipt the user holds that no node will confirm any
more.

### A double spend on unmodified code

[`n4-double-spend.sh`](repro-2026-11-13-leader-fork/n4-double-spend.sh) turns this into a double
spend. Alice pays a merchant, the merchant sees the payment as final, and Alice then spends the same
money again, this time for good.

| Step | What happened |
|---|---|
| Alice pays the merchant 900 pathUSD | Leader returns `status 1` in block 164 and reports block 170 as `finalized`. Leader shows the merchant at 1.9B and Alice at 0.1B. |
| Leader crashes and restarts | The payment is gone from every node. Alice is back to 1.0B and the merchant to 1.0B. |
| Alice pays Bob the same 900 pathUSD | `status 1` in block 203, and L1 settles the zone through block 220. |
| End state, all four nodes | Merchant 1.0B (never paid, despite a finalized success receipt). Bob 1.9B. Alice 0.1B. |

The merchant was told the payment was final. It is gone, and the same funds now sit with Bob,
settled on L1.

### A confirmed key revocation can be undone

The same crash can undo a security action, not only a payment. Zone accounts can authorise access
keys and revoke them through the AccountKeychain precompile; a key also signs tokens for the
private RPC. On unmodified code ([`keys/testA.sh`](repro-2026-11-13-leader-fork/keys/testA.sh)):

| Step | What happened |
|---|---|
| Account V authorises access key K | Durable in block 165; a K-signed transfer works |
| V revokes K | Leader returns `status 1` in block 235 and reports block 241 as `finalized`; leader shows K revoked |
| Leader crashes and restarts | The revocation is gone from every node: `getKey` shows K active, the revoke receipt is `null`, block 235 has a different hash |
| K is used again | A K-signed transfer from V succeeds in block 252; a K-signed token gets HTTP 200 from the private RPC on every node |
| Two minutes later | The revocation has not been re-included; K is still active |

A user who revokes a lost or stolen key and is told the revocation is final can be left with that key
still able to spend from the account and read its private data.

### Why the transaction can vanish rather than just move

- **Sent directly to the leader:** the transaction sits only in the leader's in-memory pool, which a
  crash wipes. Nothing re-submits it.
- **Sent through a follower or the RPC node:** the follower forwards it to the quorum and may forward
  it again, so it often lands in a later block. That is a moved transaction: same effect, different
  block, different receipt.

In Antithesis we saw both. In run `1b900239…`, tx `0xefde8a3c…` got a success receipt in block 470
from leader zone-2. zone-2 crashed before saving block 470 and rebuilt it without the transaction,
and the transaction was never included again, although L1 later settled past that height. Across
that run, 45 workload transactions had a receipt from a block that was later discarded; 22 of them
were never re-included.

### Reproducing it on unmodified code

[`repro-2026-11-13-leader-fork/n4-finalized-loss.sh`](repro-2026-11-13-leader-fork/n4-finalized-loss.sh)
runs on an image built from unmodified `8314f7ba`:

1. Pause only the leader's database-commit thread with gdb. The leader keeps producing and serving
   RPC, but nothing new is saved. This stretches the gap that normally lasts a few milliseconds per
   block.
2. Send a pathUSD transfer to the leader.
3. Kill the leader and restart it.

| Step | Result |
|---|---|
| Transfer sent to the leader | `status 1 (success)` in block 164, tx `0x89f7fbd4…5b4d` |
| Leader's `finalized` block, 3 s later | 170 |
| Leader killed and restarted | reth discards everything after block 157 (`healing via changesets checkpoint=157 sf_tip=158`) |
| Two minutes later, every node | `eth_getTransactionReceipt` returns `null`; all nodes agree on block 164, which no longer contains the transfer; sender balance unchanged (1,000,000,000 before and after) |

Antithesis caught the same pattern on unmodified product code as well. In run `cd7fa72e…`, leader
zone-0 issued a receipt for tx `0x69b24474…` in block 151 and was killed. On restart it discarded
everything after block 148 and rebuilt; the transaction ended up in block 153.

### Impact

- **Lost payments that users were told succeeded.** A wallet, exchange or merchant that treats a
  success receipt, or the `finalized` tag, as final can ship goods or credit funds for a transfer
  that never happened.
- **"Succeeded" can turn into "reverted".** A transaction that came in through a follower is often
  re-included after the crash, but under a newer timestamp, newer L1 state and a different
  ordering. A transfer that had a `status 1` receipt can execute again and fail.
- **Deposits and withdrawals are affected the same way.** A deposit credit the user saw at
  `finalized` is replayed from L1 after the crash. If an L1 policy changed in the meantime, for
  example the recipient was blacklisted, the replay bounces the deposit back instead. A withdrawal
  request (the burn on the zone) reported as final can likewise be dropped or re-executed
  differently.
- **No detection.** After the crash the chain is consistent. Nothing reports that history
  changed.
- **It needs a crash while saving lags behind.** Unlike finding 1, no follower has to be catching
  up; every block the leader has produced but not yet saved is exposed. On a healthy disk that gap is
  short: in 30 local trials where we killed the leader right after receiving a receipt, every
  transaction survived. The gap widens whenever saving slows down, for example a disk stall, a busy
  volume or heavy load. Antithesis found 45 affected transactions in one run once saving was slowed
  down, and the gdb reproduction above shows the outcome is certain once a crash lands in the
  gap.

### Suggested fix

- Do not report a block as `finalized` (or `safe`) until it is saved, and ideally until L1 has
  settled it. Keep `latest` for the in-memory head.
- Either hold receipts until the block is saved, or document receipts as provisional until the
  block is finalized, and make `finalized` mean something durable.
- Defence in depth: on restart, have the leader re-inject the transactions from discarded blocks
  into its pool before producing.

## Smaller finding: an HTTP batch keeps using a key after it has been revoked

**Severity: medium-low.** This one is separate from findings 1 and 2. It is a gap in how long an
authorisation lasts, not a crash or durability problem.

The private RPC authenticates an HTTP request once and then runs every call in a JSON-RPC batch under
that identity (`crates/zones/rpc/src/server.rs`: authentication in `handle_rpc`, then the batch
loop). Nothing re-checks the key between calls. If one call in the batch waits on L1, and
`zone_getEncryptionKey` has no timeout on its L1 calls, the key can be revoked while the batch is
still running. The later calls then return data written after the revocation.

On unmodified code ([`auth/claim2.sh`](repro-2026-11-13-leader-fork/auth/claim2.sh)), we delayed
only the RPC's L1 connection by 4–6 s. The batch was `[zone_getEncryptionKey, eth_getLogs(new blocks,
account V)]`, signed with V's access key K. While it was stalled, V revoked K and made 10 transfers:

| Run | Revoke block | A separate request with the same token | Batch result |
|---|---|---|---|
| 1 | 1890 | 403 "keychain key revoked" | 200, with 18 of V's logs from blocks 1891–1894 |
| 2 | 1925 | 403 | 200, with 16 logs from blocks 1926–1929 |
| 3 | 1949 | 403 | 200, with 16 logs from blocks 1950–1953 |

Limits:
- Only the revoked key's own account is exposed.
- The stall needs a slow L1 link, which a client cannot cause directly.
- The spec defines token rejection per request and says nothing about batches.

A fix is to re-check the token, or at least the keychain revocation and the expiry, before each call
in a batch, and to put a timeout on `zone_getEncryptionKey`'s L1 calls.

We also measured the WebSocket rule that a session authenticated by a revoked key must close within
1 s of the revoking block. In 7 runs it closed in 0.05–0.89 s, so we did not find a violation.
