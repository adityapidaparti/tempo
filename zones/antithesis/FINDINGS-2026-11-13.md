# Findings, 2026-11-13: a single leader crash can split a zone permanently

This is a new finding from the 2026-11-13 Antithesis work on the Tempo zone sequencer. It is
separate from the earlier [FINDINGS.md](FINDINGS.md) and does not repeat anything in it.

- **Code tested:** `tempoxyz/tempo@8314f7ba`, Alexey's quorum-handoff configuration
  (branch `test/zones-quorum-handoff-campaign`). The bug reproduces with the product code
  unmodified.
- **Antithesis run:** `1b900239d3de50bcf4a2b9e2cbc8ed1a-67-0` on the Tempo tenant.
- **Failing property:** *Zone nodes never hold different blocks at the same height*.

## Summary

The zone leader sometimes sends followers a block before it has finished saving that block to
its own database. If the leader crashes at that moment, it restarts without the block and builds
a different one at the same height. The followers still hold the original, so from then on they
reject everything the leader produces.

The leader carries on alone. Its RPC looks healthy and it keeps returning receipts, but
those receipts are for a chain nobody else will accept. Every other node, including the RPC node
users read from, stays at the last shared block, and L1 settlement stops because the followers
will not sign the leader's batches. Nothing in the system detects or repairs the split. The usual
remedy, handing leadership to a follower on L1 with `setLeader`, cannot work here, so an operator
has to repair the nodes by hand.

It takes one crash at the wrong moment. There is no partition and no misbehaving node.

## Background: how a zone stays in sync

A zone runs three sequencer nodes. One is the leader and produces every block; the other two are
followers. Followers receive blocks in two ways:

1. **Live broadcast.** After the leader saves a block, it pushes the block to the followers.
2. **Catch-up (backfill).** A follower that has fallen behind asks the leader for the blocks it is
   missing, in pages. A follower falls behind when it has just restarted, when a network partition
   has just healed, or when it has heard nothing for 30 seconds, in which case it probes the
   leader.

Followers never rewrite history. If a block arrives that conflicts with one they already hold,
they reject it.

## What goes wrong

Each zone node is built on reth. reth saves each block in two steps:

1. It writes the block to its *static files* and marks them complete (`finalize`).
2. It commits the database transaction (MDBX) that records the block as saved.

The block is safe only after step 2. If the process dies between the two steps, reth notices on
the next start that the static files are ahead of the database, deletes the extra block and
carries on from the last committed one. Inside reth that is correct, because no part of reth has
told anyone else about the block yet.

The zone code does tell others. To decide how far its chain goes, it asks reth for
`last_block_number()`, and that number moves forward at step 1, not step 2. So for a moment the
leader believes block H is part of its chain when H is not yet saved, and it hands H out.

The live-broadcast path does not have this problem, because it waits for reth's "block saved"
notification. Other paths ask `last_block_number()` directly. All of them are in
`crates/zones/node/src/replication.rs`, apart from settlement preparation, which is in
`crates/zones/sequencer/src/monitor.rs`:

| Where the leader publishes | What it uses the number for |
|---|---|
| Catch-up pages for followers (`serve_backfill_page`) | How far each page goes |
| The final flush when a leader hands over (`Drain`) | Which blocks to push before stepping down |
| Broadcaster start and stop | Which blocks to push |
| Settlement preparation | How far the next L1 batch may reach |

### The sequence

1. The leader produces block H. reth finishes step 1, so `last_block_number()` returns H.
2. A follower that is catching up asks for blocks. The leader serves H from memory, and the
   follower imports it and saves it to its own disk.
3. The leader crashes before step 2.
4. On restart reth deletes H. Its log shows
   `healing via changesets checkpoint=H-1 sf_tip=H`.
5. The leader is still the scheduled leader, so it builds a new block at height H. The new block
   H′ has a different hash: its timestamp comes from the wall clock, and its transactions and L1
   inputs can differ too.
6. The leader broadcasts H′. A follower holding H rejects it with *peer block conflicts with
   canonical block at height H*. It then rejects every block on top of H′ with *peer block parent
   mismatch at height H+1*, and keeps doing so.

### Why it never heals

- Followers have no way to undo a block. When a block is rejected, a follower asks the leader for
  more blocks, gets the same conflicting ones back, and rejects them again.
- The leader ignores blocks from followers and never checks that its chain matches theirs, so it
  never notices the split.
- Handing leadership to a follower with `setLeader` does not help. A follower may take over only
  from a block that already includes the handover, and the blocks leading up to it exist only on
  the old leader's chain. No node produces, so the zone stops completely.
- Repair needs an operator. Either use the manifest forced-recovery procedure to name a follower
  and the hash of H, or rebuild every node from one surviving copy. In both cases the other side's
  data has to be wiped.

## How we found it

### Where to look

We read the replication and persistence code looking for any moment when the leader could show
followers something it could still lose in a crash. The `last_block_number()` calls stood out:
reth advances that number at step 1 rather than step 2. We then confirmed in reth's source and
on running nodes that the gap is real.

### Making the window big enough to hit

Normally the gap between step 1 and step 2 is a few milliseconds per block. That is open on every
block, but random crashes rarely land in it, so we gave Antithesis two test-only tools:

- **A slow-disk fault.** A small library is loaded into each zone node. When the test switches it
  on, it delays the database's `msync`/`fsync` on `mdbx.dat` by a set number of milliseconds, up to
  45 seconds. It changes no data and no ordering; it simulates a disk that has stalled.
- **A crash driver.** Antithesis runs it alongside the normal workload. In each episode it:
  1. switches the slow-disk fault on for the leader;
  2. makes a follower fall behind, by cutting its P2P link or restarting it;
  3. lets the follower catch up;
  4. kills the leader;
  5. checks that every node agrees on every block.

The fork check is a separate always-property. It compares block hashes across all four zone
nodes at every height they have in common and fails on any difference.

### What Antithesis found

Antithesis found the split 13 minutes into the run. It ran with every fault type on the zone
nodes: crashes, pauses, CPU slowdown, network faults and clock jitter.

| Time (s) | What happened |
|---|---|
| 105.6 | Leader zone-1 starts saving block 166 on a stalled disk. Follower zone-2's P2P link is cut. |
| 107.7 | The RPC node catches up and receives block 166 (`0x7383…`) from the leader. |
| 141.3 | The link heals. zone-0 and zone-2 catch up and receive the same block 166 (`0x7383…`). |
| ~141.9 | The leader, zone-1, is killed. |
| 187.4 | zone-1 restarts, deletes block 166 (`checkpoint=165 sf_tip=166`) and resumes as leader. It builds a new block 166 (`0x3bde…`). |
| 189.85 | The fork check fails. The leader holds `0x3bde…`; the other three nodes hold `0x7383…`. |

### Reproducing it without Antithesis's help

To show the bug is in the product, not in our test tools, we reproduced it locally on a zone stack
built from unmodified `8314f7ba`, with no slow-disk library:

1. Attach gdb to the leader. Pause only the thread that performs the database commit, at the start
   of the commit. Everything else keeps running.
2. The leader stops broadcasting, because no block is ever marked saved. After 30 seconds the
   followers probe for missing blocks, and the leader serves them the unsaved one.
3. Kill the leader and start it again.

The leader lost blocks 154–156 and rebuilt all three with different hashes. We then sent a pathUSD
transfer to the leader and watched the zone for ten minutes.

| Node | Chain height | Receipt for the transfer |
|---|---|---|
| zone-0 (leader) | 1198 and rising | success, block 187 |
| zone-1 | 156, stuck | none |
| zone-2 | 156, stuck | none |
| zone-rpc (users) | 156, stuck | none |

The leader had submitted 15 settlement batches to L1 before the split and none after. Over those
ten minutes zone-1 rejected the leader's settlement proposals 1,044 times and its blocks 493
times.

The scripts are in [repro-2026-11-13-leader-fork/](repro-2026-11-13-leader-fork/), with the logs
of each run.

## Impact

- **The zone stops for everyone but the leader.** The followers and the user-facing RPC node freeze
  at the last shared block. Deposits, transfers and new withdrawals stop. Withdrawals already settled on
  L1 can still be paid.
- **Settlement stops.** A batch needs two of the three sequencers to sign, and followers sign only
  batches that match their own chain. The leader keeps proposing and never collects a second
  signature.
- **Users get receipts for transactions that will not survive.** Anything sent to the leader after
  the split gets a success receipt for a block no other node accepts. When an operator repairs the
  zone onto the followers' chain, those blocks are discarded. Transactions that came in through a
  follower may be replayed on the surviving chain, possibly with different results.
- **The outage is hard to see.** The leader's RPC keeps reporting a growing chain and successful
  transactions.
- **Recovery is manual.** `setLeader` cannot fix it, as described above.

### A worse version we have not run yet

The same gap also affects settlement. The leader decides how far a settlement batch may reach
from `last_block_number()`, and followers use the same number to decide whether they have the
block saved. Suppose this happens:

1. The leader proposes a batch ending at an unsaved block H.
2. Followers that have already received H sign the batch.
3. L1 accepts the batch.
4. The leader crashes before saving H.

L1 now records a block hash the leader no longer has. On restart the leader cannot find that block
and will not start as leader, so the node stays stuck permanently. We have traced this path through
the code but have not reproduced it yet. A run aimed at it is in progress.

## How likely it is in production

- **Every block passes through the gap.** The zone saves each block as soon as it is produced.
- **A follower is often catching up.** That happens after any restart, after any partition heals,
  and after 30 seconds without blocks.
- **The gap is short on a healthy disk** (milliseconds), but it grows with any disk stall: busy
  cloud volumes, noisy neighbours, slow `fsync`.
- **The crash can be anything:** an out-of-memory kill, a deploy, a node failure.

## Suggested fix

- Only send what is saved. Wherever the leader publishes blocks (catch-up pages, the
  handover flush, broadcaster start and stop, settlement preparation, and the followers'
  signing check), use the last block reth has reported as saved, not `last_block_number()`.
- Defence in depth: a leader that restarts behind its followers should catch up from them before
  producing again, rather than rebuilding heights it has already given out.
